  ---
  무엇이 문제인가

  1. 피드백 루프 오염

  시스템은 last_test_ok: True를 "검증된 스킬"로 취급합니다. FSALoop는 실패 시 "검증된 스킬 중 대안"을 찾고, EpisodeMatcher는 성공/실패 쌍을 학습합니다. 검증 안 된 스킬이 True로 기록되면 이   
  학습 데이터가 오염됩니다.

  2. 동작 예측 불가능

  에이전트가 "파일 압축" 스킬 요청
  → 외부 캐시에서 compress_files.py 발견
  → 토큰 겹침 점수 통과
  → 즉시 active 등록
  → 다음 턴 에이전트가 실제 파일 시스템에 실행

  그 코드가 무엇을 하는지 아무도 확인하지 않은 상태입니다.

  3. eval 결과가 의미 없어짐

  Phase 4에서 만든 trace_execution, summarize_failure, generate_eval_dataset 스킬이 있습니다. 이 eval 시스템이 존재하는 이유는 스킬 품질을 측정하기 위해서입니다. 그런데 외부 스킬은 이 경로를 
  통째로 건너뜁니다.

  ---
  "그냥 외부 소스를 신뢰하면 안 되나?"

  현재 외부 소스는 설정된 repo 캐시에서만 옵니다. 인터넷에서 랜덤으로 끌어오지 않습니다.

  그러나 문제는 신뢰 여부가 아니라 일관성입니다:

  - 내부 스킬: 개발자가 작성 → 코드 리뷰 → 테스트 → status: active
  - 외부 스킬: 캐시에서 복사 → 바로 status: active

  같은 active 상태인데 실제로 의미하는 바가 다릅니다. 시스템의 다른 컴포넌트(FSALoop, MemoryConsolidation, EpisodeMatcher)는 이 차이를 알 방법이 없습니다.

  ---
  격리가 해결하는 것

  현재:  외부 후보 → (토큰 겹침 점수) → active
  격리:  외부 후보 → draft → eval 실행 → 통과 시 candidate → 승인 → active

  draft 상태의 스킬은:
  - 에이전트에게 로드되지 않음
  - last_test_ok가 실제 eval 결과를 반영
  - 실패 시 rejected로 격리, 성공 시만 승격

  ---
  요약

  격리가 필요한 이유는 "코드 실행 전 검증" 자체보다, 시스템이 쌓아온 피드백 루프와 메모리 학습 데이터의 신뢰성을 지키기 위해서입니다.
