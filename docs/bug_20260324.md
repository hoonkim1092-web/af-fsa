# CLI 실행 오류 분석 보고서 (af -p lottery ...)

요청하신 `af -p lottery -t "데이터 기반의 로또 1등 당첨 프로그램 만들어줘"` 명령어 실행 시 발생한 연쇄적인 오류에 대한 심층 분석 결과입니다.
코드는 수정하지 않고 문제 원인과 발생 과정(Pipeline)만을 단계별로 추적했습니다.

## 🔍 핵심 원인 (Root Cause)
모든 오류의 근본 원인은 시스템에 **`GOOGLE_API_KEY`가 설정되어 있지 않기 때문**입니다.
이로 인해 `LLMEngine`의 API 통신이 원천 차단되었으며, 그 여파로 여러 가지 에러와 폴백(Fallback) 동작이 폭포수처럼 연쇄적으로 발생했습니다.

---

## 🛠️ 단계별 오류 발생 과정 추적

### Step 1: LLMEngine 초기화 실패
```text
[WARNING] No GOOGLE_API_KEY found.
[LLMEngine Error] No GOOGLE_API_KEY configured
```
- **원인:** 환경변수에 `GOOGLE_API_KEY`가 존재하지 않아 `google.genai.Client` 객체가 만들어지지 않고 `None`으로 초기화되었습니다.
- **결과:** 이후 시스템에서 발생하는 모든 AI 호출 기능(`generate()`, `generate_json()`)이 시도조차 되지 않고 즉시 에러를 내뿜거나 빈 텍스트 `""`를 반환하게 됩니다.

### Step 2: IntentGate 의 JSON 파싱 에러
```text
[IntentGate] Warning - LLM Classification failed: Expecting value: line 1 column 1 (char 0)
[Router] project pipeline selected: Keyword fallback due to LLM failure; score=3; role=general assistant
```
- **원인:** 파이프라인 진입 직후, `IntentGate`가 사용자의 명령("데이터 기반 로또...")이 어느 카테고리(greenfield, refactoring 등)에 속하는지 분류하기 위해 AI를 찔러봅니다. 앞서 말한 이유로 AI 엔진이 **빈 문자열(`""`)**을 돌려주자, 코드 내에서 이를 JSON 객체로 파싱(`json.loads("")`) 하려다가 터진 전형적인 파이썬 파싱 오류입니다.
- **결과:** 똑똑한 Factory 엔진은 예외(Exception)를 감지하고 시스템을 종료하는 대신, `Keyword fallback` (단순 키워드 기반 원시적 매칭) 모드로 회피 기동을 하여 다음 단계를 억지로 강행해 버립니다.

### Step 3: 콘솔 출력 시 한글 깨짐 (인코딩 문제)
```text
[Himari Bootstrap] "???? ?? ???? ?????: ??? ??? ?? 1? ?? ???? ????"
```
- **원인 (텍스트):** 원본 텍스트는 `"프로젝트 착수 리서치를 시작합니다."`라는 Himari 에이전트의 한국어 대사입니다. (Agent Factory 코드에 존재하는 문자입니다.)
- **원인 (시스템 불일치):** 현재 Windows 명령 프롬프트(CMD/PowerShell)의 기본 코드페이지가 옛날 방식인 확장 완성형(`CP949` / `euc-kr`) 인코딩으로 설정되어 있습니다. 반면, Python 애플리케이션은 내부적으로 `UTF-8`이라는 글로벌 표준 규격으로 한글을 출력(Print)하고 있습니다.
- **??:** UTF-8 ??? ??? ???? CP949 ??? ?? ??? ????? ??? ????? ?? `"???? ?? ???..."` ? ?? ??? ???? ??? ???.

### Step 4: 속이 텅 빈 문서들이 무더기로 생성된 이유
```text
[LLMEngine Error] No GOOGLE_API_KEY configured
============================================================
  프로젝트 문서가 생성되었습니다.
```
- **원인:** 초기 분류 이후, 실제 구조를 셋업하는 역할인 **Himari Bootstrap (리서처)** 와 **Lilith Bootstrap (PD 기획자)** 가 문서 내용을 채우기 위해 지속적으로 AI 단을 노크합니다.
- **과정:** 당연히 API 키가 없으므로 `No GOOGLE_API_KEY configured` 에러가 다시 발생합니다. 그런데 Agent Factory 코어 엔진(`core.bootstrap_roles.py` 등)은 시스템 중단을 어떻게든 막고자, 에러가 나면 코드에 하드코딩된 **빈 껍데기(Empty String)나 임의의 휴리스틱 기본값**으로 Markdown 문서와 JSON 파일들을 강제 생성해 버리도록 안전망이 설계되어 있습니다.
- **결과:** 실제 AI의 깊은 사고가 전혀 개입되지 못한 채 우회 로직만으로 파일 뼈대만 뽑혀 나왔으므로, `.md` 파일들을 열어보면 글이 없이 하얗게 비어 있는 상태로 '성공' 처리된 것입니다.

## 💡 결론 및 시스템 철학적 분석
현재 Agent Factory 아키텍처는 에러가 터져도 프로그램이 뻗지 않고 어떻게든 워크플로우를 완주하도록 **강력한 Fallback(우회) 생존 로직**이 잘 설계되어 있습니다. 에러가 났음에도 문서 체계와 디렉토리가 모두 만들어진 것이 그 반증입니다.

다만, 가장 코어가 되는 **메인 두뇌(Google API Key)** 가 연결되지 않은 상태에서 우회 로직으로만 돌파하다 보니 '영혼이 없는 텅 빈 결과물'이 생성되었을 뿐입니다. 터미널 인코딩 역시 파이썬의 표준 UTF-8 방출과 윈도우 터미널의 옛날 설정(CP949)이 부딪혀 생긴 마찰 현상입니다.
