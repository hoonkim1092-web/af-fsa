› 교차 검증이나, QA 최종 산출물 평가하는 게 agent가 생성되서 하나?
› 산출물이 제일 퀄리티 있게 나오는 방식을 택해야해 비용이 좀 더 들더라도 안정적이고 퀄리티가 높은쪽 으로 가야한다는게 내 생각이야


• 그 방향에는 동의합니다. 다만 비용을 더 써도 된다 = 모든 걸 에이전트로 돌린다는 아니고, 품질이 실제로 올라가는 구간에만 비싼 검증을 추가한다
  가 맞습니다.

  내 기준에서 최고 품질 쪽 아키텍처는 이겁니다.

  Deep Research -> Structured Artifact Draft -> Semantic Critique -> Agent QA/Execution Check -> Final Rewrite -> Aggregated Verdict

  핵심은 2번 생성하고 2번 검증하는 겁니다.

  1. Deep Research
     로컬 RAG만으로 끝내지 않고, 기본적으로 로컬 + Tavily 웹 원문 + unified RAG + 필요 시 NotebookLM synthesis까지 갑니다.
  2. Structured Draft
     산출물을 자유서술이 아니라 goal / constraints / required_skills / roles / deliverables / risks / acceptance criteria / evidence 같은 고정
     구조로 뽑습니다.
  3. Semantic Critique
     LLM 1회 판정보다 한 단계 더 강하게 갑니다.
     초안 생성 모델과 비평 모델을 분리하거나, 최소한 draft -> critique -> revise 2패스로 갑니다.
  4. Agent QA
     여기서는 정말 agent를 씁니다.
     파일 읽기, 테스트 실행, 산출물-요구사항 매핑, 누락 확인, 회귀 체크를 합니다.
     이 단계는 품질 향상 효과가 큽니다.
  5. Final Rewrite
     QA와 critique에서 나온 gap을 반영해서 최종본을 다시 씁니다.
     이 재작성 단계가 품질 차이를 크게 만듭니다.
  6. Aggregated Verdict
     최종 pass/fail은 코드 집계로 닫습니다.
     주관적 judge agent 하나에 최종 운명을 맡기지 않는 편이 더 안정적입니다.

  내가 추천하는 품질 우선 원칙은 세 가지입니다.

  - 싼 검사는 여전히 코드로 한다.
    안정성 자체가 품질이기 때문입니다.
  - 비싼 비용은 semantic critique, agent QA, final rewrite에 쓴다.
    여기서 품질이 실제로 올라갑니다.
  - 중요 산출물은 1회 생성이 아니라 생성 -> 비평 -> 수정 -> 실행검증 -> 최종수정으로 간다.

  즉 당신 생각을 더 정확히 다듬으면 이렇게 됩니다.

  비용보다 품질을 우선한다. 하지만 품질을 높이는 방식은 agent 남발이 아니라, 깊은 근거 수집 + 다단계 비평 + 실행 검증 + 최종 재작성이다.

  내 결론:
  품질 최우선이라면 지금 제안했던 3계층보다 한 단계 더 올려서 2-pass semantic review와 final rewrite를 추가하는 게 맞습니다.
  반대로 final_judge agent 하나에 맡기는 건 비싸기만 하고 안정성은 오히려 떨어질 수 있어서 추천하지 않습니다.

  목표
  최종 목표는 답변이 아니라 품질 높은 산출물입니다. 그래서 설계 기준도 빠른 응답이 아니라 아래 4개로 잡습니다.

  - 요구사항 커버리지
  - 근거의 신뢰도와 최신성
  - 실행 가능성
  - 최종 산출물의 일관성과 검증 가능성

  내가 추천하는 최종 설계는 이것입니다.

  Request
    -> Task Profiler
    -> Evidence Acquisition
    -> Evidence Verification
    -> Draft Artifact Generation
    -> Semantic Critique
    -> Gap-Driven Enrichment
    -> Revised Artifact
    -> Structural Gate
    -> Agent QA / Execution Check
    -> Final Rewrite
    -> Final Aggregator
    -> Accepted Artifact

  핵심 원칙

  - 원문이 항상 source of truth다.
  - NotebookLM은 저장소가 아니라 심층 분석기다.
  - 최종 판정은 가능하면 코드 집계로 닫는다.
  - 에이전트는 실제로 품질을 올리는 구간에서만 쓴다.
  - 중요한 산출물은 한 번 생성하지 않고 생성 -> 비평 -> 보강 -> 재작성으로 간다.

  1. Task Profiler
  입력은 사용자 요청이다.
  출력은 task_profile이다.

  이 단계에서 판단할 것:

  - 산출물 종류: brief, architecture, plan, spec, research_report, execution_plan
  - 최신성 필요 여부
  - 리스크 수준: low, normal, high
  - 외부 웹 근거 필요 여부
  - 실행 검증 필요 여부
  - 비교/의사결정형 요청 여부

  예시 출력:

  {
    "artifact_type": "architecture_plan",
    "quality_mode": "gold",
    "freshness_needed": true,
    "comparison_mode": true,
    "execution_check_required": false,
    "risk_level": "high"
  }

  2. Evidence Acquisition
  품질 우선이면 이 단계는 기본적으로 깊게 갑니다.

  순서:

  1. 로컬 RAG로 기존 문서, 코드, 메모리, 기존 planning artifact 검색
  2. 부족하거나 최신성이 필요하면 Tavily로 외부 원문 확보
  3. 웹 원문을 raw corpus로 저장
  4. 로컬 + 웹을 합쳐 unified retrieval 수행
  5. 필요하면 선별된 evidence만 NotebookLM에 넣어 심층 브리핑 생성

  중요한 규칙:

  - Tavily 결과를 그대로 소비하지 않는다.
  - raw web corpus로 저장한 뒤 재검색 가능하게 만든다.
  - NotebookLM은 원문 전체를 대신하지 않는다. 선별된 상위 근거만 넣는다.

  이 단계의 출력:

  {
    "local_references": [],
    "web_references": [],
    "raw_corpus_ids": [],
    "notebook_summary": "",
    "evidence_summary": [],
    "coverage_map": {}
  }

  3. Evidence Verification
  이 단계는 evidence 자체의 품질을 먼저 막는 단계입니다.
  산출물 생성 전에 evidence가 부실하면 뒤가 전부 흔들립니다.

  검사 항목:

  - 로컬 근거 수
  - 웹 근거 존재 여부
  - 최신성 필요한데 최신 외부 근거가 있는지
  - evidence_summary 깊이
  - NotebookLM synthesis 존재 여부
  - 핵심 엔티티 커버리지

  출력:

  {
    "status": "pass|partial|warn",
    "score": 0.0,
    "gaps": []
  }

  규칙:

  - pass면 계속 진행
  - partial이면 gap 기반으로 한 번 더 evidence 보강
  - warn이면 high-quality 모드에서는 무조건 재수집

  4. Draft Artifact Generation
  여기서 첫 번째 산출물 초안을 만듭니다.
  중요한 점은 자유형 텍스트가 아니라 구조화된 산출물로 만들어야 한다는 점입니다.

  추천 공통 스키마:

  {
    "goal": "",
    "constraints": [],
    "required_skills": [],
    "role_hints": [],
    "deliverables": [],
    "risks": [],
    "acceptance_criteria": [],
    "implementation_notes": [],
    "evidence_summary": [],
    "open_questions": []
  }

  아키텍처/플랜형 요청이면 추가:

  {
    "planning_steps": [],
    "roles": [],
    "modules": [],
    "task_slices": [],
    "verification_targets": []
  }

  이 단계는 초안 생성기 역할만 한다.
  아직 pass/fail은 판단하지 않는다.

  5. Semantic Critique
  이 단계는 품질 차이를 만드는 핵심입니다.
  단순 생성이 아니라 별도의 비평 단계가 반드시 필요합니다.

  비평 기준:

  - goal과 원 요청의 정합성
  - deliverable 누락 여부
  - 역할 분해의 적절성
  - risk마다 대응이 있는지
  - evidence 없는 주장 비율
  - acceptance criteria의 관찰 가능성
  - 기술 선택의 이유와 대안 존재 여부
  - 구현 가능한 수준의 구체성

  출력:

  {
    "status": "pass|partial|fail",
    "score": 0.0,
    "strengths": [],
    "gaps": [],
    "unsupported_claims": [],
    "revision_instructions": []
  }

  품질 최우선이면 이 단계는 1회가 아니라 2-pass가 좋습니다.

  - Pass 1: 정합성/누락 검토
  - Pass 2: 실행 가능성/검증 가능성 검토

  6. Gap-Driven Enrichment
  Semantic Critique에서 gap이 나오면 바로 재작성하지 말고, 필요한 evidence만 추가로 보강합니다.

  예:

  - 기술 선택 근거 부족 -> Tavily/로컬 문서 추가 수집
  - risk 대응 부족 -> NotebookLM comparative synthesis 요청
  - 특정 deliverable 담당 역할 없음 -> role decomposition 재계산
  - acceptance criteria 추상적 -> verification examples 추가 수집

  핵심은 비평 -> 추가 수집 -> 수정 순서입니다.
  그냥 LLM에게 “더 잘 써봐”라고 하면 품질이 안정적으로 오르지 않습니다.

  7. Revised Artifact
  Gap을 반영해 두 번째 산출물을 생성합니다.
  이 단계부터는 사실상 후보 최종본입니다.

  이 단계에서 보장할 것:

  - 모든 deliverable에 owner가 있음
  - 모든 risk에 대응 전략이 있음
  - 모든 핵심 주장에 evidence가 연결됨
  - acceptance criteria가 테스트 가능함
  - 역할/모듈/태스크가 서로 모순되지 않음

  8. Structural Gate
  이제 코드 기반의 결정론적 검사를 합니다.
  이건 품질의 하한선을 보장하는 단계입니다.

  검사 예시:

  - 필수 섹션 존재
  - 빈 필드 없음
  - 역할 수 최소 기준 충족
  - 태스크 수 최소 기준 충족
  - evidence_summary 최소 개수 충족
  - 각 역할에 required_skills 존재
  - 각 deliverable에 owner 연결
  - verification_targets 존재
  - risks와 acceptance criteria가 비어 있지 않음

  출력:

  {
    "pass": true,
    "errors": [],
    "warnings": []
  }

  품질 우선이라도 이 단계는 코드가 맞습니다.
  이건 저렴해서가 아니라, 가장 안정적이기 때문입니다.

  9. Agent QA / Execution Check
  이 단계는 실제 에이전트가 필요한 구간입니다.
  모든 요청에 항상 돌릴 필요는 없지만, 품질 최우선 모드에서는 중요 산출물에 기본 적용하는 게 좋습니다.

  qa 역할이 할 일:

  - 산출물을 실제 파일/코드/계획 관점에서 읽기
  - 요구사항과 산출물을 매핑해 누락 찾기
  - 필요하면 테스트/명령 실행
  - verification target이 실제로 검증 가능한지 확인
  - 구현 계획이 지나치게 추상적인지 확인

  evaluator 역할이 할 일:

  - 실패 원인 분석
  - retry / revise / escalate / abort 판단
  - 실패 패턴 구조화

  이 단계의 출력:

  {
    "execution_pass": true,
    "qa_findings": [],
    "regression_risks": [],
    "evaluator_action": "accept|retry|escalate|abort",
    "evaluator_advice": []
  }

  중요한 점:

  - qa_engineer는 최종 판정자가 아니다
  - qa_engineer는 실행 검증자다
  - 최종 accepted/rejected는 마지막 집계가 한다

  10. Final Rewrite
  이 단계가 실제 품질을 한 번 더 끌어올립니다.

  입력:

  - Semantic Critique의 gaps
  - Structural Gate의 warnings
  - Agent QA findings
  - Evaluator advice

  출력:

  - 최종 산출물
  - 변경 요약
  - 남은 경고

  이 단계에서 하는 일:

  - 문장 다듬기
  - 누락 보완
  - 역할/모듈/태스크 정합성 수정
  - acceptance criteria 구체화
  - evidence-linked claim 정리

  즉, 최종본은 초안이 아니라 비평과 검증을 반영한 재작성본이어야 합니다.

  11. Final Aggregator
  최종 판정은 여기서 내립니다.
  이 단계는 에이전트가 아니라 집계 로직이 맡는 게 좋습니다.

  입력:

  - evidence verification
  - semantic critique score
  - structural gate result
  - agent QA result
  - final rewrite result

  출력:

  {
    "decision": "accepted|accepted_with_warnings|rejected",
    "quality_score": 0.0,
    "blocking_issues": [],
    "warnings": [],
    "evidence_status": "",
    "semantic_status": "",
    "execution_status": ""
  }

  추천 판정 규칙:

  - accepted
    evidence pass AND structural pass AND semantic >= 0.8 AND execution pass
  - accepted_with_warnings
    structural pass AND semantic >= 0.65 AND blocker 없음
  - rejected
    structural fail 또는 semantic < 0.65 또는 execution fail

  이 설계에서 각 수단의 역할

  - 코드
    스키마, 개수, 필드, 연결 관계, 임계값, 최종 집계
  - LLM 단일 호출
    draft, critique, rewrite
  - 에이전트
    실행 검증, 파일 읽기, 테스트, 도구 사용, 실패 분석

  즉 품질 최우선이라도 모든 걸 에이전트로 하지 않습니다.
  품질이 실제로 오르는 지점만 에이전트로 올립니다.

  품질 최우선 모드의 운영 정책

  - 기본 research는 deep
  - 웹 최신성 필요한 요청은 Tavily 강제 사용
  - 중요 산출물은 NotebookLM synthesis 기본 사용
  - draft는 반드시 critique를 거침
  - critique 후 gap enrichment를 한 번 더 수행
  - high-risk artifact는 agent QA까지 강제
  - final rewrite 없이는 최종본으로 인정하지 않음

  최종 추천안
  내가 추천하는 최고 품질 모드는 아래 6단어로 요약됩니다.

  깊게 수집하고, 두 번 비평하고, 한 번 실행검증한다

  더 압축하면 이겁니다.

  Deep Evidence
  -> Draft
  -> Critique
  -> Enrich
  -> Rewrite
  -> Structural Gate
  -> Agent QA
  -> Final Rewrite
  -> Aggregated Verdict
