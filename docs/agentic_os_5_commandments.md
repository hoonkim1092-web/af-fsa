# [Agent Factory] 에이전틱 OS 5대 절대 검증 기준 (The 5 Acid Tests)

보스(User)께서 던져주신 5개의 질문은 단순한 기능 문의가 아닙니다. 이것은 일반적인 챗봇 랩퍼(Wrapper)와 **진짜 상용 에이전틱 운영체제(Enterprise Agentic OS)**를 가르는 가장 혹독하고 완벽한 **'5대 검증 기준(Acid Test)'**입니다. 

이 5가지 기준에 비춰본 현재 `Agent Factory (V22)`의 현황과 3개월 뒤 `M3 Plan`의 설계 방향을 확정합니다.

---

## 1. 지능의 근거 (Routing Log)
> **Q. "왜 Mini→Opus로 올렸는지 한 줄 로그로 항상 설명돼?"**

*   **현재 (V22)**: 안 됩니다. 단순히 에이전트 역할(아키텍트냐, 코더냐)에 따라 하드코딩된 대로 스폰될 뿐 "왜 모델을 바꿨는지" 동적 근거 로그가 없습니다.
*   **미래 (M3 Plan)**: **설계 반영 완료**. `dynamic_router.py`가 [비용/복잡도/지연시간]을 계산하여 **"왜 이 모델을 스폰(Spawn)했는지"**에 대한 결정 근거(Reasoning)를 1줄짜리 JSON 메타데이터로 만들어, 반드시 메인 이벤트 버스(Hub)의 **Immutable Audit Trail(영구 감사 로그)**에 박제하도록 통제합니다. 

## 2. 보안과 권한 통제 (Policy Enforcement)
> **Q. "삭제/권한/시크릿 접근은 정책으로 무조건 막거나 승인으로 가?"**

*   **현재 (V22)**: 절반 구동 중. `security_guard.py`가 코드 단위에서 `rm -rf`나 탈옥 코드를 정적으로 막고 있으며, `policy.yaml`에서 쓸 수 있는 툴 자체를 제한합니다.
*   **미래 (M3 Plan)**: **완벽한 거버넌스**. 에이전트에 **Capability Token**이 부여되며, `DB Drop` / `Network SSH` 같은 치명적(High Risk) 이벤트는 버스를 지나가는 순간 파이프라인이 즉각 정지(Suspend)되고 인간(Boss)의 결재판[Approve/Reject] 대기열로 강제 이관됩니다.

## 3. 격리 실행과 영향도 분석 (Sandbox Diff & Impact Radius)
> **Q. "샌드박스에서 리허설 후 diff/영향 범위를 보여주고 승인 받아?"**

*   **현재 (V22)**: 샌드박스가 없고 바로 로컬에 반영 및 실행(`Terminal Run`)해버립니다. (가장 위험한 부분)
*   **미래 (M3 Plan)**: **설계 반영 완료**. M3 거버넌스의 **[시나리오 모의 테스트 (Sandbox Eval)]** 티어가 이 역할을 합니다. 에이전트가 짠 코드를 메인망이 아닌 컨테이너(가상망)에서 리허설(Compile/Dry-run)해 본 뒤, 기존 대비 **어떤 로직(Diff)이 바뀌고 எந்த 시스템에 영향을 끼치는지 리포트**를 뽑아 버스(Hub)에 올려서 최종 검증 심판관(Reasoning Judge)이나 인간의 승인을 받습니다.

## 4. 벤더 독립적 아키텍처 (Agnostic Governance)
> **Q. "모델 바꿔도(Claude→Gemini→OpenAI) 시스템이 동일 정책/동일 로그로 돌아?"**

*   **현재 (V22)**: 완벽하게 가동 중입니다. `AgentRunner`가 LLM API 호출부를 독립된 추상 계층으로 감싸놓았기 때문에, Claude가 대답하든 Gemini가 대답하든 파싱 로직, 스킬(Tool) 권한 통제, 로깅은 **100% 동일하게 팩토리 규칙(Policy)를 탑니다.**
*   **미래 (M3 Plan)**: 이 원칙(Agnostic)이 **Agent Factory OS의 가장 강력한 코어 밸류이자 해자(Moat)**입니다. 벤더가 누구든 팩토리의 거버넌스 문지기 앞에서는 얄짤없습니다.

## 5. 자동화된 장애 복구 체계 (State Machine Failover)
> **Q. "실패했을 때 “재시도/승급/롤백”이 상태 머신으로 고정돼?"**

*   **현재 (V22)**: 에러가 나면 하위 에이전트가 "에러 났으니 어떻게 할지 다시 알려줘"라며 핑퐁을 칩니다. 단순 루프만 있을 뿐 '상태 머신(State Machine)'의 개념은 없습니다.
*   **미래 (M3 Plan)**: **설계 반영 완료**. `Cascade Failover (폭포수 롤백)`이 바로 이 상태 머신입니다.
    *   **Phase 1 (재시도/Retry)**: 일시적 429 에러 -> 2초 대기 후 동종 모델로 재호출.
    *   **Phase 2 (승급/Upgrade)**: "컨텍스트 한계 도달" 또는 "3회 이상 AST 검사 탈락(로직 오류)" -> 작업의 난이도 지표를 상향 조정하여 **더 높은 지능(예: Sonnet -> Opus)으로 승급 스폰**.
    *   **Phase 3 (롤백/Rollback)**: 그래도 답이 없으면 이벤트를 Drop하고 메인 버스에 "작업 실패: 보상 트랜잭션(이전 코드 복구) 가동"을 브로드캐스트.
